# Denials Automation MVP — Feasibility Validation Spec

**Status:** Draft for engineering review
**Scope:** Medical Necessity + DRG Downgrade
**Date:** April 2026

---

## 1. Purpose

This document defines the technical scope, data requirements, evaluation methodology, and success criteria for a time-boxed feasibility validation of automated denials management for two denial types: **Medical Necessity (Med Nec)** and **DRG Downgrade**.

The goal is not to build a production system. The goal is to answer four questions with enough rigor to make a build/no-build decision:

1. Can we reliably extract structured data from payer denial letters (PDFs)?
2. Can we link denial letters to remit data and derive clean outcome labels?
3. Does our existing appeal writer produce letters that win?
4. What is the baseline win rate, and what features correlate with winning?

---

## 2. Scope

### In scope

- Medical Necessity denials (all payers represented in existing PDF corpus)
- DRG Downgrade denials (all payers represented in existing PDF corpus)
- Denial PDF letters already uploaded to the appeal writer
- 835 remit data from the same client accounts
- Appeal letters generated by the appeal writer for those same cases

### Out of scope (for this phase)

- ADR (separate track — different data pipeline)
- New data collection from clients not already in the system
- Payer portal integrations or submission automation
- Production-grade infrastructure, scaling, or compliance review
- Any model training (this phase is evaluation only — no training runs)

---

## 3. What We're Validating

### 3.1 Extraction fidelity

Can our PDF parser pull the fields we need from denial letters with sufficient accuracy?

Denial letters are unstructured and vary significantly by payer. Before anything else, we need to know our extraction accuracy on the fields that drive downstream logic.

### 3.2 Linkage rate

What percentage of denial PDFs in our corpus can be reliably linked to a corresponding 835 remit record? Without this linkage, we cannot derive outcome labels at scale.

### 3.3 Outcome labeling quality

Given a linked denial + remit pair, can we derive a clean outcome label (overturned / upheld / partial)? We need to understand how much this can be automated vs. requires human review.

### 3.4 Appeal writer performance

For cases where we have denial letter + appeal letter + outcome, what is the win rate? Are there patterns in cases that win vs. lose that we can act on?

## 4. Data Inventory

### 4.1 What we have

| Asset | Format | Notes |
|---|---|---|
| Denial letters | PDF | Uploaded by users to appeal writer. Mix of payers, med nec + DRG downgrade. Volume TBD — need count. |
| Appeal letters | PDF or text | Generated by appeal writer for the above cases. Should map 1:1 to denial letters. |
| 835 remit files | EDI 835 or parsed JSON | From same client accounts. Contains claim-level payment, adjustment codes (CARC/RARC), and DRG paid. |

### 4.2 Key unknowns — answer before starting

Before engineering begins, product/ops needs to resolve:

- **How many denial PDFs do we have total, per type?** We need at minimum 200 med nec + 200 DRG downgrade cases with outcomes to have statistically meaningful results. If we're below that, the feasibility study itself needs a data acquisition step first.
- **Are the denial PDFs already associated with a claim ID or account ID?** If not, linkage to remit data requires probabilistic matching (patient name + DOS + payer), which adds engineering complexity.
- **What date range do the remit files cover?** If denials are recent and remit files don't extend far enough forward, outcomes may not yet be resolved (appeal still pending).
- **Do we have the appeal letters for all denial cases, or only a subset?** The appeal quality analysis requires the triad: denial letter + appeal letter + outcome.

## 5. Data Pipeline

### 5.1 Overview

```
Denial PDFs
    │
    ▼
[PDF Extraction Service]  ──→  Structured Denial Record
    │
    │   + 835 Remit Data
    ▼
[Linkage Engine]  ──→  Linked Denial-Remit Pair
    │
    ▼
[Outcome Labeling]  ──→  Labeled Dataset
    │
    │   + Appeal Letters
    ▼
[Evaluation Layer]  ──→  Feasibility Report
```

### 5.2 Stage 1 — Denial PDF extraction

For each denial letter PDF, extract the following fields:

**Common fields (both types):**

| Field | Description | Example |
|---|---|---|
| `payer_name` | Insurance company name | "Blue Cross Blue Shield" |
| `denial_type` | Med Nec or DRG Downgrade | "Medical Necessity" |
| `patient_name` | As written on letter | "Margaret Holloway" |
| `member_id` | Payer member/subscriber ID | "BCB-774112-MH" |
| `claim_number` | Payer claim reference number | "CLM-8847291" |
| `date_of_service` | DOS or date range | "2026-02-11 – 2026-02-15" |
| `date_of_denial` | Date letter was issued | "2026-03-01" |
| `carc_code` | Claim Adjustment Reason Code | "CARC-50" |
| `rarc_code` | Remittance Advice Remark Code | "M86" |
| `denial_rationale_text` | Full text of the denial reason | Raw text block |
| `criteria_cited` | Clinical guideline cited (MCG/InterQual) | "MCG-A-0226" |
| `appeal_rights_text` | Appeal deadline and process | Raw text block |

**DRG Downgrade additional fields:**

| Field | Description | Example |
|---|---|---|
| `drg_billed` | DRG as billed on original claim | "MS-DRG 291" |
| `drg_paid` | DRG assigned by payer | "MS-DRG 292" |
| `drg_delta_description` | How payer described the change | "MCC not supported by documentation" |
| `drg_weight_billed` | Relative weight of billed DRG | 3.1072 |
| `drg_weight_paid` | Relative weight of paid DRG | 1.9441 |

**Med Nec additional fields:**

| Field | Description | Example |
|---|---|---|
| `level_of_care_denied` | What level of care was denied | "Inpatient admission" |
| `criteria_not_met` | Specific criteria payer says weren't met | "Milliman SI.23.1 — acute inpatient criteria" |
| `suggested_alternative` | What payer suggested instead | "Observation status" |

**Extraction confidence scoring:**

Each extracted field should carry a confidence score (0–1). Fields below a configurable threshold (suggested: 0.80) should be flagged for human review rather than passed downstream automatically. Track per-field accuracy separately — some fields (payer name, denial date) will be near-perfect; others (criteria cited) will be harder.

**Extraction target accuracy (minimum to proceed):**

| Field | Target accuracy |
|---|---|
| payer_name | ≥ 98% |
| claim_number | ≥ 95% |
| denial_type classification | ≥ 95% |
| date_of_service | ≥ 92% |
| carc_code | ≥ 90% |
| criteria_cited | ≥ 75% |
| drg_billed / drg_paid | ≥ 92% |

If extraction accuracy falls below these thresholds on your payer mix, the pipeline is not viable without prompt engineering work or a fine-tuning step.

### 5.3 Stage 2 — Linkage to 835 remit

Match each extracted denial record to its corresponding 835 payment record.

**Primary linkage key:** `claim_number` — if the denial letter contains the payer's claim reference number and the 835 uses the same identifier, this is a deterministic match.

**Fallback linkage (if claim number unavailable or mismatched):** probabilistic match on `(member_id, date_of_service, billed_amount)`. Flag all fallback matches for human validation before including in the labeled dataset.

**Per-record output after linkage:**

```json
{
  "denial_id": "...",
  "claim_number": "CLM-8847291",
  "linkage_method": "claim_number | probabilistic",
  "linkage_confidence": 0.97,
  "remit_record": {
    "paid_amount": 8240.00,
    "denied_amount": 4210.00,
    "carc": "CARC-4",
    "drg_paid": "MS-DRG 292",
    "payment_date": "2026-03-15"
  }
}
```

**Track and report:**
- Total denial PDFs in corpus
- % successfully linked to a remit record
- % linked via primary key vs. fallback
- % unlinked (and reason: no matching remit, date mismatch, etc.)

A linkage rate below 70% is a hard blocker — it means the dataset is too incomplete to draw conclusions.

### 5.4 Stage 3 — Outcome labeling

Derive outcome label from the linked denial + remit pair.

**Automated labeling rules:**

| Condition | Label |
|---|---|
| Post-denial payment ≥ 95% of denied amount | `overturned_full` |
| Post-denial payment between 10–94% of denied amount | `overturned_partial` |
| No subsequent payment found within 180 days of denial date | `upheld_or_pending` |
| Subsequent payment = $0, case closed in system | `upheld` |

**The `upheld_or_pending` ambiguity is the key data quality problem.** A case with no subsequent payment could mean the appeal was filed and lost, the appeal was never filed, or the appeal is still in flight. You cannot use these cases in win-rate calculations without additional resolution. Options:

1. Cross-reference against appeal letters: if an appeal letter exists, the case was worked. If no subsequent payment exists after 180 days, label as `upheld`.
2. Manual review sample: pull a random 50-case sample of `upheld_or_pending` and have a billing team member classify them. Use this to estimate the error rate of the automated labeling and apply a correction factor.

**Target: ≥ 80% of linked cases should have a clean automated label** (not `upheld_or_pending`). If you're below this, your remit data coverage window is likely too short.

## 6. Evaluation Methodology

### 6.1 Win rate baseline

Once you have a labeled dataset, compute:

- **Overall win rate** by denial type (med nec, DRG downgrade)
- **Win rate by payer** — critical, because payer behavior varies dramatically
- **Win rate by denial subtype** (e.g. inpatient admission vs. length of stay for med nec; MCC stripping vs. CC stripping for DRG)
- **Win rate by appeal letter source** (was an appeal letter generated? which version of the writer?)
- **Median days to resolution** for won vs. lost cases

This baseline is the single most important output of the feasibility study. If your win rate is already 80%+, automation adds efficiency. If it's 30%, you have an effectiveness problem that automation alone won't solve.

### 6.2 Appeal letter quality evaluation

For cases that have a denial letter, an appeal letter, and an outcome label, run a structured human evaluation on a sample of 50–100 cases (mix of wins and losses).

Score each appeal letter on:

| Criterion | Scale | Description |
|---|---|---|
| Clinical accuracy | 1–5 | Does the letter accurately represent the patient's clinical picture? |
| Criteria response | 1–5 | Does the letter directly address the payer's stated criteria? |
| Specificity | 1–5 | Are specific diagnoses, procedures, dates, and values cited? |
| Persuasiveness | 1–5 | Would a clinician reviewer find this compelling? |
| Format compliance | 1–5 | Is it structured per the payer's preferred appeal format? |

**Evaluators:** ideally a mix of an experienced appeals specialist and a physician advisor. At minimum, one person with appeals experience who can grade blind (without knowing the outcome).

Correlate quality scores with outcomes: do higher-scoring appeal letters actually win more? If there's no correlation, quality scoring isn't a useful signal. If there is a correlation, it becomes a training signal.

### 6.3 Denial letter feature analysis

For the labeled dataset, run a correlation analysis between denial letter features and outcome. Key questions:

- Does the specific payer criteria cited predict outcome? (e.g. cases citing MCG criterion X win at 60%, criterion Y at 20%)
- For DRG: does the DRG weight delta predict difficulty? (larger delta = harder to win?)
- For med nec: does "suggested alternative" being observation vs. outpatient predict outcome?
- Does denial date proximity to deadline correlate with win rate? (rushed appeals lose more?)

This analysis does not require ML — it's descriptive statistics. The goal is to find signals that can inform prioritization logic (which cases to work first, which to escalate to physician review).

## 7. Success Criteria

The feasibility study passes if all of the following are true:

| Criterion | Pass threshold | Notes |
|---|---|---|
| Denial PDF extraction accuracy | ≥ 90% on key fields | Evaluated on 100-case human-reviewed sample |
| Linkage rate | ≥ 70% of denial PDFs link to a remit record | |
| Clean outcome label rate | ≥ 80% of linked cases | Excludes `upheld_or_pending` |
| Total labeled cases | ≥ 200 per denial type | Minimum for statistical validity |
| Win rate signal | Statistically significant difference between at least two payer segments | p < 0.05 |
| Appeal quality-outcome correlation | Spearman ρ ≥ 0.3 | Quality scores correlate with win rate |

If extraction accuracy or linkage rate fail, the blockers must be resolved before evaluating the rest. If the labeled dataset is too small, data acquisition is the next step — not modeling.

---

## 8. What We Are NOT Doing in This Phase

It's worth being explicit about what this phase does not include, so the engineering team doesn't over-build:

- **No model training.** This is a data quality and signal validation exercise. We are evaluating whether the data supports a model, not building one.
- **No new client data collection.** We work with what's already in the system.
- **No payer portal integrations.** Submission automation is a phase 2 problem.
- **No real-time pipeline.** Everything runs as a batch evaluation job.
- **No compliance review.** PHI handling follows existing data practices — no new data sharing arrangements.

## 9. Phasing and Timeline

### Phase 0 — Data audit (Week 1–2)

**Owner:** Product + Engineering
**Deliverable:** Data inventory doc

- Count denial PDFs by type and payer
- Assess remit data date range and coverage
- Confirm claim ID linkage methodology
- Determine if we have ≥ 200 cases per type; if not, define acquisition plan
- Identify whether appeal letters are stored and retrievable

**Go/no-go gate:** If we have fewer than 100 linked cases per type, pause and define a data acquisition strategy before proceeding.

---

### Phase 1 — Pipeline build (Week 3–6)

**Owner:** Engineering
**Deliverable:** Working extraction + linkage + labeling pipeline

Extraction service:
- Extend existing PDF parser to output the structured schema defined in Section 5.2
- Add per-field confidence scoring
- Flag low-confidence extractions for human review queue

Linkage engine:
- Implement primary linkage (claim number match against 835)
- Implement fallback probabilistic linkage
- Output linkage confidence score per record

Outcome labeling:
- Implement automated labeling rules (Section 5.4)
- Flag `upheld_or_pending` cases for manual review queue
- Output labeled dataset as flat file (CSV or JSON)

Human review tooling:
- Simple internal UI (or spreadsheet workflow) for reviewing flagged extractions and `upheld_or_pending` cases
- Does not need to be production-quality

---

### Phase 2 — Evaluation (Week 7–8)

**Owner:** Product + Clinical
**Deliverable:** Feasibility report

- Run extraction + linkage on full corpus
- Compute linkage rate and label rate
- Compute win rate baseline by type, payer, subtype
- Run human appeal letter quality evaluation on 50–100 cases
- Correlation analysis: quality scores vs. outcomes, denial features vs. outcomes
- Write up findings against success criteria in Section 7

---

### Phase 3 — Decision (Week 9)

**Owner:** Leadership
**Deliverable:** Go/no-go decision on each denial type

Present findings and make one of three calls per denial type:
- **Build** — data is sufficient, signal is strong, proceed to production design
- **Invest in data first** — signal looks promising but dataset is too small; define data acquisition strategy
- **Deprioritize** — win rate is low for reasons outside automation's control (e.g. payer behavior), focus resources elsewhere

## 10. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Denial PDFs are too payer-heterogeneous to extract reliably | Medium | High | Run extraction on a 20-case pilot sample before committing to full pipeline build. If accuracy is below threshold, invest in prompt engineering before Phase 1. |
| Linkage rate is low because claim IDs don't appear in denial letters | Medium | High | Validate linkage methodology on 20-case sample in Phase 0. If deterministic match fails, scope fallback matching before Phase 1. |
| Remit data doesn't extend far enough forward to resolve outcomes | Low-Medium | High | Check date ranges in Phase 0. If appeals take 90–180 days, ensure remit files go far enough to capture resolutions. |
| Appeal letters are not stored or retrievable for historical cases | Medium | Medium | Quality evaluation is still possible on new cases going forward. Historical win rate analysis doesn't require the appeal letter — just the outcome. |
| Win rate too low for automation to matter | Low | High | This is actually a valuable finding. Surfaces either an effectiveness problem (appeal writer needs improvement) or a selection problem (we're appealing cases we shouldn't). |
| PHI handling in evaluation pipeline | Low | High | Ensure evaluation jobs run within existing compliant infrastructure. No exfiltration of patient data to external tooling (e.g. no sending raw denial letters to third-party APIs without BAA). |

## 11. Open Questions

These need answers from product/ops before engineering begins:

1. **Volume:** How many denial PDFs do we have per type? Are they tagged by type already, or do we need to classify them first?
2. **Linkage:** Do payer denial letters reliably include the original claim number? Which payers do and don't?
3. **Appeal letter storage:** Are generated appeal letters stored and retrievable? Are they associated with the denial they were written for?
4. **Remit coverage:** What date range does our 835 remit data cover per client? Do we have enough runway to see resolved outcomes?
5. **Client consent:** Do our existing agreements permit using uploaded denial letters and remit data for internal model evaluation? (Likely yes under existing BAAs but should be confirmed.)
6. **Evaluator availability:** Who will do the human appeal quality evaluation? Can we get a billing/appeals specialist and a physician for 4–8 hours in week 7–8?
7. **Payer criteria access:** Do we have licensed access to MCG or InterQual criteria? If not, the "criteria response" quality dimension in the appeal evaluation may be hard to score accurately.

## 12. Appendix — Denial Type Reference

### Medical Necessity denial pattern

```
Payer denies claim on grounds that the level of care billed was not medically
necessary per their clinical criteria. Typically cites a specific guideline
(MCG, Milliman, InterQual) and asserts one or more criteria were not met.

Common CARC: CARC-50 (non-covered because not deemed medically necessary)
Common RARC: M86, MA01, N432

Key variables:
- Which guideline was cited?
- Which specific criterion was not met?
- Was an alternative level of care suggested (obs, outpatient)?
- Is the denial first-level or reconsideration?
```

### DRG Downgrade denial pattern

```
Payer accepts the claim but assigns a lower-weight DRG than billed, resulting
in a reduced payment. Typically driven by stripping a CC or MCC that payer
claims is not sufficiently documented.

Common CARC: CARC-4 (claim/service denied — insufficient documentation)
Common RARC: N115

Key variables:
- What DRG was billed vs. paid?
- What weight delta does that represent in dollars?
- Which diagnosis or procedure drove the billed DRG that payer stripped?
- Is this a CC strip (lower impact) or MCC strip (higher impact)?
```
